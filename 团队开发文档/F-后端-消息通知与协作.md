## 2. 关键设计

### 2.1 提醒体系（NFR-12，R-12 风险主责）

| 任务 | cron | 逻辑 |
|---|---|---|
| 截止提醒 | 每日 09:00 / 21:00 | 扫描 activity/competition/goods/buddy_post `deadline ∈ [now, D+7/3/1]` → notify_message（dedup_key 幂等）→ T-1 晚追加模板消息 |
| 报名开始 | 每日 08:00 | enroll_start 到达且未报名用户（依据收藏/浏览意向） |
| 订单超时 | 每分钟 | 付款 30min 超时取消 / 确认 72h 关闭（与 G 的状态机联动，扫描走 G 提供的 Service，写入走我方通知） |
| 组织者降权 | 每日 10:00 | 活动开始前 24h 未响应 → 降权 + 通知报名者（BS-08） |

- 幂等三保险：dedup_key 唯一索引 + Redis 分布式锁 + 心跳监控埋点（《16》§6，09:30 未执行告警）；
- 模板消息频控：单用户单业务 5 条/小时；发送失败重试 3 次后转站内 only（R-12 多通道）。

### 2.2 申请中心状态机

```
direction=1 申请：0 待处理 → 1 通过 / 2 拒绝 / 4 补充询问（→申请人答复回 0）
                  申请人可 3 撤回（仅待处理态）
direction=2 邀请：被邀请人 agree / reject / consider
通过 → team_member 写入 + TIM 建群/入群（REST）+ 双方通知（队伍通知：加入/退出/角色调整）
```

并发处理同一申请：乐观锁（同《12》§3），后到者 40007。

### 2.3 TIM 集成边界

- 后端只做：userSig 签发、群组生命周期 REST（建群/拉人/踢人/发系统消息）、业务卡片消息体定义 `{linkType, linkId, title}`；
- 消息体存储交 TIM 云端留存（《03》取舍：不自研 IM）；我方仅存会话元数据（用于"删除本地会话"后可恢复）。

## 3. 接口依赖与被依赖

- 依赖：D 权限、G 的订单超时扫描点、E 的 NotifyEvent 投递方约定；
- 被依赖：M2/M4/M5/M6 全部把"发通知"委托给我（只许调 NotifyService.send，禁止直写 notify_message 表——模块边界检查项）；
- 前端 C 是消息页/申请中心消费方，角标聚合接口是双方高频契约。

## 5. 自测 DoD

- [ ] 提醒幂等：同一竞赛同一天重复执行任务仅 1 条通知（TC-M3-06）；
- [ ] 真机模板消息到达率抽测 ≥ 99.9%（NFR-12，W11 前完成）；
- [ ] 申请并发处理无脏数据；撤回仅限待处理态；
- [ ] 08:59 批量截止场景不堆积不重发（PT-04）；
- [ ] 被屏蔽用户不产生任何通知与 IM 可达（与 E 联测 TC-M2-11）。
