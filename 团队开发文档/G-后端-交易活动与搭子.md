## 2. 关键设计

### 2.1 订单状态机（《11》§3.3，TC-M4 重点）

```
10 待卖家确认 ──卖家确认──▶ 30 待面交 ──双方确认──▶ 50 已完成
      │ 30min 未付款 ──▶ 60 已取消            │
      └─卖家拒绝/取消 ──▶ 60                  ├─单方确认──▶ 40 待确认 ──另一方确认──▶ 50
                                              └─72h 无双方确认──▶ 70 超时关闭
非法跳转一律 40007（ST-05 抓包改 status 用例的防线）
```

- **并发与幂等**：状态迁移一律乐观锁 `UPDATE goods_order SET status=? WHERE order_no=? AND status=?`；face-confirm 各自 `WHERE confirm_at IS NULL` 更新，后确认方触发 40→50 迁移（接口示例见《13》§4）；
- **联系方式可见性**：seller_confirm 前 contact_info 对 buyer 脱敏（40003 语义在字段层体现，防骚扰 FR-M4-04）；
- **超时任务**：F 的每分钟任务调用本模块 `OrderTimeoutService.scan()`，本模块只负责状态迁移与事件，通知由 F 发。

### 2.2 报名体系（活动/竞赛同构）

- 唯一约束 `uk_ae(activity_id, user_id)` 防重复报名（40006，BS-04）；
- 截止校验：`now > enroll_deadline → 40007 已截止`（BS-05）；
- capacity 满员 → 拒绝并提示候补（TC-M5-05）；
- 组织者审核 approve/reject → 通知报名者（NotifyEvent bizType=50）；
- **降权钩子**：活动开始前 24h 未响应审核 → F 降权任务回调本模块（BS-08）。

### 2.3 竞赛日历

`GET /competitions/calendar?month=` 返回该月四类节点（报名起止/初赛/决赛/截止）的日期聚合，前端渲染月历（TC-M5-07）；数据源即 competition 表时间列，无冗余表。

### 2.4 搭子匹配

- gender_limit=1 的帖仅女性用户可见/可申请（TC-M6-03，服务端判定 gender）；
- 申请通过 → 双方解锁联系方式（同订单脱敏策略）+ buddy_post.matched=1（"我滴过的"）+ NotifyEvent(20)；
- 匹配度百分比 = 标签重合度简单加权（爱好 0.6 + 同校 0.2 + 活跃 0.2），纯计算无模型（《03》：低成本高感知）。

### 2.5 信用分（P2）

互评 → credit_log 流水（delta/原因/关联单）→ user.credit_score 汇总；< 60 触发发布限制（发布接口前置检查 40003 语义，TC-M4-10）。

## 3. 接口依赖与被依赖

- 依赖：D 权限与机审（发布类）、E 的搜索（求购匹配）、F 的 NotifyEvent 与超时任务调用；
- 被依赖：A（首页四宫格数据源之一）、B（商品/搭子/活动竞赛表单）、C（组织者操作页、我的记录）；
- 负载提示：本模块横跨 M4/M5/M6 三域，W4–W7 与 W12–W15 为双高峰，超期 3 天即触发 F 接手预案（《19》§2.2）。
